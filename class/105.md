# 1. The Real Attribute Lookup Order

Before descriptors, you must understand **how Python finds attributes**.

When you do:

```python
obj.x
```

Python internally executes:

```python
type(obj).__getattribute__(obj, "x")
```

And the lookup order is roughly:

```
1. Data descriptor in class
2. Instance __dict__
3. Non-data descriptor in class
4. Class attribute
5. __getattr__()
```

Memorize this. **Frameworks depend on this behavior.**

We will revisit this after learning descriptors.

---

# 2. What Is a Descriptor

A **descriptor** is simply an object implementing any of these methods:

```python
__get__(self, instance, owner)
__set__(self, instance, value)
__delete__(self, instance)
```

If an object with these methods is stored **inside a class**, Python gives it **special behavior during attribute access**.

Example:

```python
class Descriptor:
    def __get__(self, instance, owner):
        print("Getting value")
        return 42


class A:
    x = Descriptor()


a = A()
print(a.x)
```

Output:

```
Getting value
42
```

Why?

Because `x` is a **descriptor**, so Python calls:

```python
Descriptor.__get__(descriptor_obj, a, A)
```

instead of returning the object directly.

---

# 3. Understanding `__get__`

Signature:

```python
__get__(self, instance, owner)
```

Parameters:

| parameter | meaning                      |
| --------- | ---------------------------- |
| self      | descriptor object            |
| instance  | instance accessing attribute |
| owner     | class owning descriptor      |

Example:

```python
class Descriptor:
    def __get__(self, instance, owner):
        print("self:", self)
        print("instance:", instance)
        print("owner:", owner)
        return "value"


class A:
    x = Descriptor()

a = A()
print(a.x)
```

Output:

```
self: <Descriptor object>
instance: <A object>
owner: <class A>
```

---

## Access from class

```python
print(A.x)
```

Output:

```
instance: None
owner: <class A>
```

This is **intentional design**.

Frameworks use this to distinguish:

```
A.field -> field definition
a.field -> field value
```

**Django ORM fields behave like this.**

# 4. `__set__`

Controls assignment.

Example:

```python
class Descriptor:

    def __get__(self, instance, owner):
        return instance._value

    def __set__(self, instance, value):
        print("setting value")
        instance._value = value


class A:
    x = Descriptor()


a = A()
a.x = 10
print(a.x)
```

Output:

```
setting value
10
```

The assignment:

```
a.x = 10
```

becomes:

```
Descriptor.__set__(descriptor, a, 10)
```

# 6. Data vs Non-Data Descriptors (VERY IMPORTANT)

Descriptor types:

### Non-data descriptor

Implements only:

```
__get__
```

Example:

```
methods
functions
```

---

### Data descriptor

Implements:

```
__get__ + __set__
```

or

```
__get__ + __delete__
```

---

### Why this matters

Because **data descriptors override instance attributes**.

Example:

```python
class Descriptor:
    def __get__(self, instance, owner):
        return "descriptor value"


class A:
    x = Descriptor()


a = A()
a.x = "instance value"

print(a.x)
```

Output:

```
instance value
```

Because:

```
instance dict wins over non-data descriptor
```

---

Now make it **data descriptor**:

```python
class Descriptor:

    def __get__(self, instance, owner):
        return "descriptor value"

    def __set__(self, instance, value):
        pass
```

Now:

```
descriptor value
```

Because:

```
data descriptor wins over instance dict
```

Remember:

```
Data descriptor > instance attribute > non-data descriptor
```

Frameworks rely heavily on this rule.

# 7. Methods Are Descriptors

Functions in classes are **non-data descriptors**.

Example:

```python
class A:
    def hello(self):
        print("hello")


print(A.hello)
```

Output:

```
<function A.hello>
```

Now:

```python
a = A()
print(a.hello)
```

Output:

```
<bound method A.hello of <A object>>
```

What happened?

Python internally executed:

```
function.__get__(instance, owner)
```

Which returns a **bound method**.

Equivalent to:

```python
A.hello.__get__(a, A)
```

This is how Python auto-injects `self`.

---

# 8. How `property` Works

`property` is just a descriptor.

Simplified version:

```python
class Property:

    def __init__(self, fget):
        self.fget = fget

    def __get__(self, instance, owner):
        return self.fget(instance)
```

Usage:

```python
class User:

    def __init__(self, name):
        self._name = name

    @property
    def name(self):
        return self._name


u = User("raj")
print(u.name)
```

Internally:

```
User.name.__get__(u, User)
```

# 9. Real Production Example — ORM Field

This is exactly how **Django / SQLAlchemy fields work**.

Example:

```python
class Field:

    def __init__(self, name):
        self.name = name

    def __get__(self, instance, owner):
        return instance.__dict__.get(self.name)

    def __set__(self, instance, value):
        if not isinstance(value, int):
            raise ValueError("must be int")

        instance.__dict__[self.name] = value


class User:

    age = Field("age")


u = User()

u.age = 30
print(u.age)
```

Output

```
30
```

This is **exactly how ORM validation happens**.

# 10. Lazy Loading Descriptor (Very Common)

```python
class LazyProperty:

    def __init__(self, func):
        self.func = func

    def __get__(self, instance, owner):

        value = self.func(instance)

        setattr(instance, self.func.__name__, value)

        return value
```

Usage:

```python
class Data:

    @LazyProperty
    def expensive(self):
        print("computing...")
        return 42


d = Data()

print(d.expensive)
print(d.expensive)
```

Output:

```
computing...
42
42
```

Computed **only once**.

# Final Mental Model

When Python sees:

```
obj.attr
```

It does roughly:

```
if attr in class and attr is data descriptor:
    call descriptor

elif attr in instance dict:
    return instance value

elif attr in class and attr is non-data descriptor:
    call descriptor

elif attr in class:
    return class attribute

else:
    call __getattr__
```

# More on Descriptors (Gemini)

To understand descriptors, you first have to realize that in Python, when you type `obj.x`, a lot of "magic" happens behind the scenes. Descriptors are the machines that power that magic.

A **Descriptor** is simply a Python object that implements at least one of these three methods in its class: `__get__`, `__set__`, or `__delete__`.

---

### 1. The Two Types of Descriptors

The distinction between them depends entirely on which methods they implement.

#### **Non-Data Descriptors**

These only implement `__get__`. They are typically used for things that are "read-only" or provide a computation.

* **Example:** A standard method or a `@staticmethod`.
* **Behavior:** If you assign a value directly to the instance (e.g., `obj.x = 10`), the instance dictionary (`__dict__`) takes over, and the descriptor is "shadowed" (ignored).

#### **Data Descriptors**

These implement both `__get__` and `__set__` (and/or `__delete__`).

* **Example:** `@property`.
* **Behavior:** These are "stubborn." Even if you try to set a value in the instance `__dict__`, the data descriptor **always** takes precedence. You cannot shadow a data descriptor easily.

---

### 2. Why do we need to study them?

You might not write descriptors every day, but you use them in almost every line of Python code. You study them to understand:

* **How Properties Work:** The `@property` decorator is just a convenient way to create a data descriptor.
* **How Methods Work:** In Python, functions are actually non-data descriptors. When you call `obj.method()`, the descriptor's `__get__` method is what "binds" the instance to the function to create `self`.
* **Lookup Order:** It explains why sometimes your instance variables override class variables and sometimes they don't.

---

### 3. What's their benefit?

Descriptors give you **total control** over attribute access.

* **Validation:** You can use `__set__` to ensure a value is always an integer or within a certain range before it's even stored.
* **Lazy Evaluation:** You can use `__get__` to calculate a value only when it's requested (like a database connection) and then cache it.
* **Clean API:** They allow you to turn a simple attribute access (`user.age`) into a complex logic gate without changing the syntax for the person using your class.
* **Code Reuse:** You can write a `Validator` descriptor once and use it across ten different classes, rather than writing `if/else` logic in ten different `__init__` methods.

---

### A Practical Example

Here is a "Type Checker" descriptor. It ensures an attribute can only be a string.

```python
class StringField:
    def __init__(self, name):
        self.name = name

    def __get__(self, instance, owner):
        return instance.__dict__.get(self.name)

    def __set__(self, instance, value):
        if not isinstance(value, str):
            raise TypeError(f"{self.name} must be a string!")
        instance.__dict__[self.name] = value

class User:
    name = StringField("name") # This is the descriptor

u = User()
u.name = "Alice"  # Works!
u.name = 123      # Raises TypeError: name must be a string!

```

------------------------------------------------------------------------------------

The `@property` decorator is the most common way to use **data descriptors** in Python. It allows you to define a method that can be accessed like a simple attribute (e.g., `user.age` instead of `user.get_age()`).

Its main benefit is that it lets you add logic (validation, computation, or protection) without changing how the outside world interacts with your class.

---

### 1. The "Protected Attribute" (Validation)

This is the most frequent use case. You want to make sure a value (like a price or age) is never negative.

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        self._price = price  # Internal attribute

    @property
    def price(self):
        """The getter: returns the value."""
        return self._price

    @price.setter
    def price(self, value):
        """The setter: adds validation logic."""
        if value < 0:
            raise ValueError("Price cannot be negative!")
        print(f"Modifying price to {value}")
        self._price = value

item = Product("Laptop", 1000)
item.price = 950   # Works like a normal attribute
# item.price = -50 # This would raise a ValueError!

```

---

### 2. Computed Attributes

Sometimes you want an attribute that isn't stored, but is calculated on the fly based on other data.

```python
class Square:
    def __init__(self, side):
        self.side = side

    @property
    def area(self):
        """Calculated every time it's accessed."""
        return self.side ** 2

shape = Square(5)
print(shape.area) # 25
shape.side = 10
print(shape.area) # 100 (automatically updates)

```

---

### 3. Read-Only Attributes

By defining a `@property` without a corresponding `.setter`, you effectively make that attribute read-only.

```python
class User:
    def __init__(self, user_id):
        self._user_id = user_id

    @property
    def user_id(self):
        return self._user_id

me = User(99)
print(me.user_id) 
# me.user_id = 100 # AttributeError: can't set attribute

```

---

### Why is this better than a standard method?

* **Encapsulation:** You can start with a simple attribute `self.price = 10`. If you later realize you need validation, you can turn it into a `@property` without breaking anyone else's code that uses `obj.price`.
* **Clean Syntax:** It keeps your API "Pythonic." Users of your class don't have to call `get_price()` and `set_price()`.
* **Control:** You decide exactly how an attribute is read, written, or deleted.

---

### Comparison of Descriptor Types

| Type | Example | Methods | Precedence |
| --- | --- | --- | --- |
| **Data Descriptor** | `@property` | `__get__`, `__set__` | **Highest** (Overrides instance `__dict__`) |
| **Non-Data Descriptor** | Regular method | `__get__` | **Lower** (Instance `__dict__` wins) |
----------------------------------------------------------------------------------------------------------------

Great observation! You’ve hit on the "naming dance" that makes properties work.

In short: **Yes**, the method name must match the attribute name you want the outside world to use. But there is a specific reason why we use `_price` (with an underscore) inside the class.

---

### 1. The "Public" vs "Private" Name

When you use `@property`, you are creating a **virtual attribute**.

* **The Method Name (`price`):** This becomes the "Public API." When someone types `item.price`, Python sees the `@property` decorator and says, *"Wait, don't look for a variable named price; run the function named price instead."*
* **The Internal Name (`_price`):** We need a place to actually store the data. If we named the internal variable `self.price`, the setter would call itself in an infinite loop!

---

### 2. Why the Underscore `_` matters

The underscore is a convention in Python that tells other developers: *"This is internal; please don't touch it directly."*

Look what happens if we don't use the underscore:

```python
@price.setter
def price(self, value):
    # If we used self.price here...
    self.price = value  # This triggers the setter again!
    # ...which triggers the setter again... INFINITE RECURSION.

```

By using `self._price`, the setter can save the value into a "real" variable without re-triggering the "virtual" property logic.

---

### 3. The Execution Flow

When you run your code, here is exactly what Python does behind the curtain:

1. **`item.price = 950`**: Python checks if `price` is a property.
2. **It is!**: It calls the `@price.setter` method and passes `950` as the `value`.
3. **Validation**: The code checks `if 950 < 0`.
4. **Storage**: It executes `self._price = 950`. This is just a simple variable assignment; it doesn't trigger any methods.
5. **Accessing**: When you later do `print(item.price)`, it calls the `@property` (getter) which simply returns the value hidden in `self._price`.

---

### Summary of the Naming Rules

| Component | Name | Purpose |
| --- | --- | --- |
| **Getter Method** | `price` | The name the user types to **get** the value. |
| **Setter Method** | `price` | The name the user types to **set** the value. |
| **Storage Variable** | `_price` | Where the data actually lives in memory. |

---

### A Small Correction in your `__init__`

To make your code even safer, you should call the **property** inside your `__init__` instead of setting `self._price` directly. This ensures validation happens even when the object is first created:

```python
def __init__(self, name, price):
    self.name = name
    self.price = price  # No underscore! This triggers the setter logic immediately.

```

If you do this and try to create `Product("Bad", -10)`, it will crash instantly with your "Price cannot be negative!" error.

---------------------------------------------------------------------------------------------------------

It’s a very smart intuition to worry about that, but **no**, it won't cause infinite recursion if you use the underscore correctly!

The recursion only happens if the **setter** tries to assign to the **exact same name** as the property. By using `self._price` (with the underscore) inside the setter, you break the loop.

### How the "Internal" variable saves you

Think of it like a "Front Door" (the property) and a "Storage Room" (the variable).

1. **The Front Door (`self.price`):** This is where people enter. When they do, the setter "guard" checks their ID (validation).
2. **The Storage Room (`self._price`):** Once the guard approves, they put the item in the storage room.

---

### Let's trace the execution:

If you change your `__init__` to `self.price = price`:

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        # 1. This calls the "Front Door" (the @price.setter)
        self.price = price 

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative!")
        
        # 2. This stores the value in the "Storage Room"
        # Since this name (_price) is DIFFERENT than the setter name (price),
        # it does NOT trigger the setter again. No recursion!
        self._price = value 

```

### When WOULD it cause recursion?

You would get a `RecursionError` only if you did this inside the setter:

```python
    @price.setter
    def price(self, value):
        # ERROR: This calls the setter again... which calls the setter again...
        self.price = value 

```

### Why the correction is "Smarter"

By using `self.price = price` in the `__init__`, you are forcing the data to go through the "Guard" (the setter) even during the object's birth.

If you use `self._price = price` in the `__init__`, you are "sneaking" the data into the storage room through the back door, skipping the validation. This could result in a product having a negative price if someone initializes it incorrectly!

---

### Summary Table

| Statement | Triggers Setter? | Use Case |
| --- | --- | --- |
| `self.price = 10` | **Yes** | Use this in `__init__` to ensure data is valid from the start. |
| `self._price = 10` | **No** | Use this **only** inside the setter to actually save the data. |

----------------------------------------------------------------------------------------------------------------------

To understand why this doesn't loop forever, you have to visualize the "hand-off" between the public name (`age`) and the internal storage (`_age`).

Here is the step-by-step execution flow for your code:

### Phase 1: Object Initialization (`p = Person('Rajat', 26)`)

1. **`Person.__init__` starts**: Python allocates memory for the object `p`.
2. **The first line runs**: `self.age = age`.
3. **The Trigger**: Python looks at the `Person` class and sees a **data descriptor** (the `@property` and `@age.setter`) named `age`.
4. **The Redirection**: Instead of creating a variable in `p.__dict__`, Python automatically redirects this assignment to the `age(self, value)` setter method.
5. **Validation**: Inside the setter, `value` is `26`. The check `if value < 0` is false.
6. **Storage**: The line `self._age = value` runs. Crucially, because `_age` (with an underscore) is **not** a property, Python simply creates a standard entry in the object's dictionary: `p.__dict__['_age'] = 26`.
7. **Completion**: The `__init__` finishes setting `self.name = 'Rajat'`.

---

### Phase 2: Updating the Value (`p.age = 100`)

1. **The Call**: You type `p.age = 100`.
2. **The Interception**: Again, Python sees that `age` is a property with a setter. It intercepts your command.
3. **The Setter runs**:
* It prints: `Modifying age to 100`.
* It executes `self._age = 100`.


4. **The Result**: The internal "storage room" `_age` is updated to `100`. The "front door" `age` remains the gateway for future access.

---

### Phase 3: Accessing the Value (e.g., `print(p.age)`)

1. **The Request**: You ask for `p.age`.
2. **The Getter runs**: Python sees the `@property` decorator on the `def age(self)` method.
3. **The Retrieval**: The method returns `self._age`.
4. **Output**: You get `100`.

---

### Visualizing the Internal Dictionary (`p.__dict__`)

If you were to peek inside the object's actual memory using `print(p.__dict__)`, you would see this:

```python
{
    'name': 'Rajat',
    '_age': 100
}

```

Notice that **`age`** (the property) is not in the dictionary. It lives on the **Class** level, acting as a traffic controller. Only **`_age`** lives on the **Instance** level as actual data.

### Summary of the "No Recursion" Rule

* `self.age = 100` calls the **function**.
* `self._age = 100` writes to the **memory**.
* Because the names are different, the function doesn't call itself.
-------------------------------------------------------------------------------------------------------------------

That is the best way to truly understand how the "magic" works! When we use `@property`, Python is actually using a **Descriptor** class behind the scenes.

Let's build a "Custom Property" from scratch without using any decorators. This will show you exactly how Python intercepts the `self.age` call.

### The "Manual" Property (The Descriptor)

We will create a class called `IntegerOnly`. Its job is to act as the "Guard" for any attribute we give it to.

```python
class IntegerOnly:
    def __init__(self, storage_name):
        self.storage_name = storage_name  # e.g., "_age"

    def __get__(self, instance, owner):
        print(f"Fetching {self.storage_name}...")
        return instance.__dict__.get(self.storage_name)

    def __set__(self, instance, value):
        if not isinstance(value, int):
            raise TypeError(f"{self.storage_name} must be an integer!")
        print(f"Setting {self.storage_name} to {value}")
        instance.__dict__[self.storage_name] = value

class Person:
    # We define the 'age' attribute using our custom descriptor
    age = IntegerOnly("_age")

    def __init__(self, name, age):
        self.name = name
        self.age = age # Triggers __set__

```

---

### Why this is powerful

1. **Reusability:** Unlike `@property`, which you have to rewrite for every single attribute, you can use `IntegerOnly` for `age`, `height`, `weight`, etc., without repeating your `if isinstance` logic.
2. **The Lookup Chain:** When you call `p.age`, Python looks at the **Class** `Person` first. It sees `age` is a "Data Descriptor" (it has `__set__`), so it ignores the instance dictionary and runs our `__get__` method instead.

### The Execution Trace

If you run `p = Person("Rajat", 26)`:

1. `Person.__init__` calls `self.age = 26`.
2. Python sees `Person.age` is an instance of `IntegerOnly`.
3. It calls `IntegerOnly.__set__(age_descriptor, p, 26)`.
4. Our code checks if `26` is an `int`, then saves it into `p.__dict__['_age']`.

---

### Comparison: `@property` vs. Custom Descriptor

| Feature | `@property` | Custom Descriptor |
| --- | --- | --- |
| **Setup** | Fast and easy for one-off logic. | More code initially, but reusable. |
| **Logic** | Lives inside the `Person` class. | Lives in its own separate class. |
| **Best for** | Simple calculated fields (like `area`). | Large-scale validation (like Database fields). |

# Lazy Loading Descriptor

A **Lazy Loading descriptor** (often called a "cached property") is a specialized **Non-Data Descriptor**. Its job is to perform a heavy calculation the first time you ask for it, then store that result so subsequent requests are lightning-fast.

The "trick" relies on the **Python Lookup Chain**: if a descriptor only has `__get__` (and no `__set__`), Python will check the instance's `__dict__` *first* before calling the descriptor.

---

### The Code: A Custom `LazyProperty`

Here is how you build one from scratch. Imagine we have a `Database` class that takes a long time to connect.

```python
import time

class LazyProperty:
    def __init__(self, function):
        self.function = function
        self.name = function.__name__

    def __get__(self, instance, owner):
        # If called on the class (Database.connection), return the descriptor itself
        if instance is None:
            return self

        # 1. Run the "heavy" function
        print(f"--- Computing '{self.name}' for the first time ---")
        value = self.function(instance)

        # 2. Store the result directly in the instance's __dict__
        # This "shadows" the descriptor for all future calls!
        instance.__dict__[self.name] = value
        
        return value

class Database:
    def __init__(self, db_name):
        self.db_name = db_name

    @LazyProperty
    def connection(self):
        time.sleep(2)  # Simulate a heavy 2-second task
        return f"Connected to {self.db_name} at {time.time()}"

# Execution
db = Database("Production_DB")

print("Request 1:")
print(db.connection)  # Takes 2 seconds, runs __get__

print("\nRequest 2:")
print(db.connection)  # Instant! Fetched from db.__dict__['connection']

```

---

### How the "Magic" Works (The Lookup Chain)

The reason this is so efficient is how Python resolves `obj.attribute`:

1. **Step 1:** Is `attribute` a **Data Descriptor** (has `__get__` AND `__set__`) in the class? (No, our `LazyProperty` only has `__get__`).
2. **Step 2:** Is `attribute` in the **Instance `__dict__**`?
* *First Call:* No. So it moves to Step 3.
* *Second Call:* **Yes!** Our descriptor put it there during the first call. Python returns that value and **ignores the descriptor entirely**.


3. **Step 3:** Is it a **Non-Data Descriptor**? Yes. Run `__get__`.

---

### Why use this?

* **Performance:** You don't waste CPU/Memory on attributes the user might never actually click on or request.
* **Startup Speed:** Your `__init__` stays lightweight because the heavy lifting is deferred.
* **Encapsulation:** The user doesn't need to know the data is being cached; they just access `db.connection` like a normal variable.

### Built-in Alternative

In modern Python (3.8+), you don't actually have to write this yourself! You can use the built-in decorator:

```python
from functools import cached_property
```
