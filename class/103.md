# 3. Namespaces and Attribute Lookup

You already started this topic.

Topics:

* instance namespace
* class namespace
* attribute lookup algorithm
* `__dict__`
* attribute shadowing
* attribute overriding

Full lookup order:

```
data descriptor
instance dict
class dict
non-data descriptor
MRO
__getattr__
```
---
# 1. Instance Namespace

Every object instance has its **own storage for attributes**.

That storage is the **instance dictionary**.

```python
class User:
    pass

u = User()

u.name = "Rajat"
u.age = 25

print(u.__dict__)
```

Output

```
{'name': 'Rajat', 'age': 25}
```

Meaning:

```
instance
   |
   ---> __dict__  (attribute storage)
```

Key point:

```
instance attributes live in instance.__dict__
```

Production insight:

Every time you do:

```python
obj.x = 10
```

Python is doing:

```python
obj.__dict__['x'] = 10
```

---

# 2. Class Namespace

Classes also have a namespace.

But **class attributes live in the class dictionary**.

Example:

```python
class User:
    role = "admin"
```

Check it:

```python
print(User.__dict__)
```

You’ll see something like:

```
{
 'role': 'admin',
 '__init__': ...,
 '__module__': ...,
 '__dict__': ...
}
```

Key idea:

```
class attributes live in class.__dict__
```

So we now have **two storage locations**:

```
instance.__dict__
class.__dict__
```

---

# 3. Attribute Lookup Algorithm (Simplified)

When you do:

```python
obj.attr
```

Python **does NOT directly read obj.**dict****.

It runs an **algorithm**.

Simplified version:

```
1. data descriptor
2. instance.__dict__
3. class.__dict__
4. non-data descriptor
5. parent classes (MRO)
6. __getattr__()
```

We will focus first on **instance vs class**, because 90% bugs happen here.

---

# 4. Instance vs Class Lookup

Example:

```python
class User:
    role = "admin"

u = User()

print(u.role)
```

Where is `role`?

```
User.__dict__
```

But Python still finds it.

Why?

Lookup process:

```
1. check u.__dict__  -> not found
2. check User.__dict__ -> found
```

So result:

```
admin
```

---

# 5. Attribute Shadowing

Now watch carefully.

```python
class User:
    role = "admin"

u = User()

u.role = "guest"

print(u.role)
```

Output:

```
guest
```

Why?

Because now:

```
u.__dict__ = {'role': 'guest'}
User.__dict__ = {'role': 'admin'}
```

Lookup:

```
1. check instance dict  -> found guest
2. stop search
```

So class value is **ignored**.

This is called:

```
attribute shadowing
```

Instance attribute **shadows** class attribute.

Production bug example:

```python
class Config:
    timeout = 30

cfg1 = Config()
cfg2 = Config()

cfg1.timeout = 5
```

Now:

```
cfg1.timeout = 5
cfg2.timeout = 30
```

Junior engineers panic here.

---

# 6. Attribute Overriding (Subclass)

Now inheritance.

```python
class A:
    x = 10

class B(A):
    x = 20

b = B()

print(b.x)
```

Output:

```
20
```

Why?

Because lookup:

```
b.__dict__ -> not found
B.__dict__ -> found 20
```

Parent class not needed.

---

Example 2:

```python
class A:
    x = 10

class B(A):
    pass

b = B()
print(b.x)
```

Lookup:

```
b.__dict__ -> none
B.__dict__ -> none
A.__dict__ -> 10
```

Result:

```
10
```

This search order is called:

```
MRO (Method Resolution Order)
```

For this code:

Memory model:

```
b (instance)
 |

 |

 |
 |-- __dict__ = {'y': 2}
 |
A (parent class)
 |

```

Lookup for:

```
b.z -> instance
```

# 9. Important Production Gotcha

Class attributes that are **mutable**.

Example:

```python
class A:
    items = []

a1 = A()
a2 = A()

a1.items.append(10)

print(a2.items)
```

Output:

```
[10]
```

Why?

Because:

```
items lives in class.__dict__
```

Both instances share it.

This bug appears **constantly in production**.

Correct version:

```python
class A:
    def __init__(self):
        self.items = []
```

Now each instance gets its own list.

# 10. Real Production Example (PyTorch)

In PyTorch:

```python
class MyModel(nn.Module):
    def __init__(self):
        self.linear = nn.Linear(10, 5)
```

When you assign:

```
self.linear
```

PyTorch intercepts it via **descriptor logic** and registers the layer.

This relies **heavily on Python attribute lookup rules**.

If you don’t understand this topic, PyTorch internals look like magic.

# Exercise 2

Your answer:

```

[1]
```

Correct result.
But your explanation is **not precise enough**.

You said:

> mutable data structure causing modification

That is **not the real reason**.

The real reason:

```
items exists only in class.__dict__
```

Memory layout:

```
A.__dict__ = {'items': []}

a.__dict__ = {}
b.__dict__ = {}
```

When Python executes:

```python
a.items.append(1)
```

Lookup:

```
a.__dict__ -> not found
A.__dict__ -> found list object
```

Then:

```
append(1)
```

This **mutates the SAME list object**.

So both instances see:

```
[1]
```

Important difference:

### Mutation

```
a.items.append(1)
```

does NOT create an instance attribute.

### Assignment

```
a.items = [1]
```

would create:

```
a.__dict__['items']
```

shadowing the class attribute.

This distinction causes **real production bugs**.

# One More Production Example

```python
class Service:
    retries = 3

s = Service()

s.retries += 1
```

What happens?

Most engineers think:

```
class retries becomes 4
```

Wrong.

Actual steps:

```
1 lookup s.retries -> found in class (3)
2 compute 3 + 1
3 assign to instance
```

Result:

```
Service.retries = 3
s.retries = 4
```

Memory:

```
Service.__dict__ = {'retries': 3}

s.__dict__ = {'retries': 4}
```

This happens **a lot in configs and frameworks**.
